# ADR-010: Run the flash sale in its own cell, and load-test it open-loop
**Status:** Accepted
**Context:** A 500k req/s spike sharing pods, Redis and DB connections with normal catalog/checkout would slow the whole store. Separately, our first Locust/JMeter plans were closed-loop, which hides stalls (coordinated omission): in our model a 2 s stall showed p99 = 1 ms closed-loop vs 1,902 ms open-loop.
**Decision:** (1) The sale runs in a dedicated **cell**: its own pod set, Redis, PgBouncer pool and rate limits, routed by `sale_id` at the edge; regular traffic runs in other cells; cells per region (and per tenant later). Inside the cell, Envoy uses power-of-two-choices on in-flight count with outlier ejection. (2) All load tests are **open-loop**: Locust schedules Poisson arrivals at a fixed rate and records latency from the intended start time (HdrHistogram); JMeter uses the Precise Throughput Timer with a worker pool sized by Little's law (10,000/s × 0.5 s = 5,000 threads).
**Alternatives:** One shared cluster with autoscaling (too slow for a 1 s spike, no blast-radius limit); per-service bulkheads only (still share DB and cache); closed-loop thread-per-user tests (under-report tail latency exactly when it matters).
**Consequences:** + Sale overload or a bad deploy stays inside one cell; latency numbers we quote are honest. − Duplicate infrastructure to pre-provision and pay for during the sale; a cell router to maintain; open-loop tests need a large enough worker pool or they silently become closed-loop again.
